## 置き方

1. 調査の後、`kizashi render <lead_id> --run <run_id> --public`（候補のメモ）か `kizashi render <run_id> --public`（実行の概要）で、伏せた写しを `data/runs/<run_id>/public/` に書きます。受注者名は「受注者A」などに、法人番号は「法人番号（伏せ字）」に替わります。
2. 記者が写しを読み、公開するものを選んで `examples/` に写します（実行のフォルダーを丸ごとは写しません）。引用には、候補と関係のない受注者名や法人番号が入ることがあります（一覧表のページの引用は、文末までの決まりで長くなります。D-086）。伏せ字と `check --publish` が当てるのは、その実行の公表一覧にある受注者名・法人番号と同じ文字列だけなので、表記の違う名前や公表一覧にない名前は伏せられません。公開する写しとデモ動画では、引用の中の名前も記者が確かめます。
3. 写したファイルを `examples/publish.manifest` に1行ずつ書きます。
4. 公開用のコミットを手元で作ります（`git add` と `git commit`。この時点では push しません）。検査は、一覧と、ステージと、最新のコミットの `examples/` の一覧が一致することを求めるので、コミットの前は `P_MANIFEST_MISMATCH` になります。
5. そのコミットで `kizashi check --publish examples/publish.manifest --run <run_id>` を通します（下の「公開の検査」）。
6. 通ったら、検査の後に何も変えずに、そのコミットを公開します（push します）。不合格なら push せず、直してから手元のコミットを作り直し（`git commit --amend`、または `git reset` で取り消してから作り直す）、もう一度検査します。作り直す前のコミットは、ほかのブランチやタグから参照していなければ、検査の対象（すべての参照からたどれる履歴）から外れます。すでに push した履歴にあったものは、作業フォルダーを直しても消えないので、新しいリポジトリを作り直します。

## publish.manifest（公開するファイルの一覧。記者が書く）

- 1行に1つのパスを、リポジトリの直下から書きます（`examples/` の中だけ）。空行と `#` で始まる行は読みません。
- 一覧のファイル自身は、書かなくても一覧に入ります。
- `examples/` にコミットするファイルは、このファイル（`README.md`）と `disclosure.allow` も含めてすべて書きます。一覧と、ステージの一覧（`git ls-files examples/`）と、最新のコミットの一覧（`git ls-tree -r --name-only HEAD examples/`）が一致しなければ、不合格（`P_MANIFEST_MISMATCH`）です。

## disclosure.allow（伏せない名前。記者が書く）

- 記者が照会を済ませたなど、出してよいと判断した受注者名か法人番号（13桁）だけを、1行に1つ書きます。このファイルは記者が作ります（ひな形はありません）。
- すべての行を名前として読みます。説明やコメントの行は書きません（`#` で始まる行も名前として読みます）。値は NFKC にして比べます。
- ここにある名前は、`render --public` で伏せず、`check --publish` で不合格にしません。記号（受注者A など）は、この一覧にある名前も含めて割り当てるので、名前を足しても、ほかの受注者の記号は変わりません（D-056⑤）。
- ここに書くことは、その名前の公開を記者が認めたことを意味します。知識ファイル（`references/`）の19行が実データの受注者名と同じ文字列で不合格になる件（D-054）でも、記者が名前と掲載の文脈を確かめ、公開を認めたものだけをここに書きます。知識ファイル全体を検査から外す規則はありません。
- コミットするなら、`publish.manifest` に `examples/disclosure.allow` を書きます。

## 公開の検査（`kizashi check --publish`）

```text
export KIZASHI_DENYLIST=/リポジトリの外の/publish_denylist.txt
kizashi check --publish examples/publish.manifest --run <run_id> [--run <run_id> ...]
```

- `KIZASHI_DENYLIST` は、補助資料4点のファイル名と中身の SHA-256 の一覧です（リポジトリの外に置きます）。1行に `<SHA-256> <ファイル名>`（`sha256sum` の出力の形）で、4点を1行ずつ書きます。環境変数がない、読めない、形が誤っている、または行・異なるハッシュ・異なる名前のどれかが4つでない場合は `E_DENYLIST_MISSING`（終了コード3）になり、合格にしません。
- `--run` で指定した実行の原本と台帳から、氏名の一覧、取り込まない列の値（担当官の所在地と相手方の住所）、受注者名、法人番号の一覧を、検査のたびに作ります（保存しません）。`--run` がなければ `E_BAD_ID` です。
- 検査の対象は `examples/` だけではありません。作業フォルダーの一覧のファイル、ステージのすべての中身、すべての参照からたどれる履歴のすべての中身を見ます。不合格（終了コード1）では場所（パス、blob、行、履歴ならそのコミット）だけを返し、見つけた語は書きません。
- 履歴で見つかったものは、作業フォルダーを直しても公開物から消えません。履歴の書き換えは自動では行わないので、新しいリポジトリを作り直します。
- 氏名・取り込まない列の値・受注者名・法人番号を検査するのは、UTF-8 として読めて 5MB 以下の中身だけです。それ以外（Shift_JIS の CSV、PDF、画像、表計算のファイルなど）は補助資料のハッシュだけを照らし、氏名などは検査しません。合格のメッセージと `targets.hash_only` にその数が出るので、0件でなければ、その中身は記者が開いて確かめます。
- P0 の検査は、一覧の一致、補助資料の中身とファイル名、氏名と取り込まない列の値、`disclosure.allow` にない受注者名・法人番号の4項目です。APIキーなどの秘密の書式、個人の絶対パス、表計算で数式として評価される文字列（P1）、まだ取り込んでいない遠隔の履歴、`--all` に入らない参照（reflog だけに残るもの）は検査しません。
- 公開するのは、この検査を通したコミットそのもの（検査の後に変えていないもの）だけにします。
