# KIZASHI

公開データの年度比較で見つけた変化について、理由を公表資料で調べ、「比較成立」「見かけの変化」「保留」のどれかを結論にした調査メモを返すツールである。メモは調査の端緒で、不正の指摘ではない。記事にするか、どう使うかは記者が決める。

最初の分野は、内閣府の公共調達（競争入札・随意契約の契約の公表のCSVとPDF）である。分野の設定（`datasets/cao-procurement/dataset.yaml`）が読めるのは令和5〜8年度で、令和8年度は年度途中として扱う。

環境分野（NITE の PRTR 個別事業所データ）は、分野アダプタの骨組み（`datasets/prtr/` の設定・型付きの表・検出SQL 1本・合成のテスト用データ。仕様は `docs/adapter_prtr.md`）だけを作った。取得・正規化・検証からメモまでは通していないので、2つの分野で動くことは実証していない。示せるのは、分野を追加できる設計であることまでである（設計書8.3・8.4。`kizashi run prtr` は分野の登録がないので `E_USAGE` で止まる）。

- 設計：`docs/harness_design_m_v06.md`（設計書）
- 実装の仕様：`docs/implementation_spec.md`、内閣府のデータの仕様：`docs/adapter_cao_procurement.md`
- 決めたことと未決の点：`docs/decisions.md`

## 何をするか

1. 記者と Claude が問いと年度を決め、`kizashi run` が公表一覧のCSVとPDFを取得し、品質検査をして、年度間の変化（契約金額、契約方式、随意契約の理由）の候補を検出する。
2. Claude が候補を最大3件選び、仮説と取り下げ条件を先に書き、公表資料（追加資料は最大12件）で理由を調べる。比較を誤らせる6つの型（制度・定義の変更、集計範囲・期間の違い、業務・数量の変化、価格・市場の条件、主体の同一性、取り込み・公表形式・元の記載の誤り）を一つずつ当てる。
3. `kizashi check` が、数値の計算、引用と原本の照合、根拠、比較の条件、結論の要件を検査する（検証 V1〜V8）。合格した内容だけを `kizashi render` がメモに書く。

件数・金額・比率は Claude が計算せず、`kizashi` の計算記録から出す。メモの数値は「7,793,940円（令和6年度の合計。計算K0012）」のように計算IDに戻れる。資料にない係数（税込と税抜の換算、按分、物価の補正など）は使わず、要るときは記者に提案する。

## 記者の役割

| 誰が | すること |
| --- | --- |
| 記者 | 問い・年度・母集団の絞り込み（指示するときだけ）を決める。メモの「記者の確認リスト」の行を原本で確かめる。係数の提案を使うか決める。記事にするか、公開するかを決める |
| Claude（調査のセッション） | 候補を選び、仮説・同種業務の対応・主張・判定・取材質問・結論の案を、`inbox/` の提案ファイルに書いて `kizashi record` で登録する。`check` の不合格を読んで直す（修正は2巡まで） |
| `kizashi`（CLI） | 取得、正規化、品質検査、検出、計算、引用の照合、検証、メモの書き出し。台帳（SQLite）にすべての記録を残す |

`check` の合格は、機械の検査に通ったことで、記者が確かめたことではない。メモの冒頭には常に「調査用・記者未確認」と出る。

## 必要なもの

- OS：macOS・Linux・WSL2（ネイティブの Windows は確かめていない。設計書11.2の U5）。この開発は WSL2 で行った。
- Python 3.13（リポジトリの `.python-version`）。標準の `sqlite3` の SQLite が 3.44 以上であること。3.44 未満なら、`kizashi` は起動時に `E_USAGE` で止まり、版を示す（実装仕様1章、D-016）。
- [uv](https://docs.astral.sh/uv/)（依存は `pyproject.toml` と `uv.lock` で固定）
- Claude Code（調査のセッション）。入れてログインし、`claude --version` で版を確かめておく（起動スクリプトが版を実行の記録に残す）。権限の設定を確かめた版は v2.1.318（D-001）。ほかの版では、起動のモードと権限の規則が同じように効くかを確かめてから使う。
- 通信：取得は許可リストのホスト（`*.go.jp`、`*.lg.jp`）の HTTPS だけ。

## 調査の始め方

調査は、リポジトリの直下で次のように起動する（開発には使わない）。

```text
scripts/investigate
```

`scripts/investigate` は、`uv sync --frozen` の後、Claude Code を次の設定で起動する：許可したものだけが動くモード（`--permission-mode dontAsk`）、プロジェクトの設定だけを読む（`--setting-sources project`）、使えるツールを Bash・Read・Grep・Glob・Skill・WebSearch・Write に絞る、調査用の設定 `investigate.settings.json` を足す。このセッションの許可の一覧にあるのは、`inbox/` 直下の `.json` と `.sql` への書き込みと、Bash の `kizashi` の7つの操作（`run`・`fetch`・`inspect`・`query`・`record`・`check`・`render`）、Skill、WebSearch である。Skill は Claude に「Bash では kizashi だけを使い、ファイルを読むときは Read・Grep・Glob を使う」と指示している（運用の指示。D-071）。ただし、指示と、実行が機械的に拒否されることは別で、拒否を実機で確かめたのは次の範囲である（Claude Code v2.1.318・v2.1.319。`docs/decisions.md` の D-001・D-017・D-071）：`inbox/` の下のフォルダーや `.json`・`.sql` 以外への書き込み、`src/`・`docs/`・`README.md` などへの書き込み、`python3`・`curl`・`jq`、書き込みのできる Bash のコマンド（`docs/` への `cp` と `src/` への `touch` は D-071 の前の試験で拒否を確かめた。そのときのモードは記録にない。D-071 で拒否の一覧に足した後は `mkdir` を dontAsk と accept edits の両方で確かめた。accept edits でほかのコマンドは試していない）、WebFetch・サブエージェント（道具がない）。`tail` などの読み取りだけのコマンドが拒否されるかは確かめていない（Read で読める範囲と同じ）。MCP と `git push` は設定で拒否しているが、実機では試していない。操作が拒否されたら、Claude は何をしようとして拒否されたかを記者に伝える（権限を広げる方法は案内しない）。

起動したら、次のどちらかで始める。

```text
/investigate cao-procurement      # 新しい調査（分野を指定）
/investigate <run_id>             # 続きから（実行IDを指定）
```

流れ（`.claude/skills/investigate/SKILL.md`）：

1. Claude が `datasets/cao-procurement/README.md` を読み、記者と問いと比べる2年度を決めて `inbox/run-config.json` を書き、`kizashi run cao-procurement --config inbox/run-config.json` を実行する。実行IDは `20261106-132648-3zdx` の形。
2. `kizashi inspect <run_id>` で品質検査・検出の件数と候補の一覧を読み、詳しく調べる候補を最大3件選ぶ（選んだ理由を記者に伝える）。
3. 候補ごとに、仮説と取り下げ条件、同種業務の対応、主張、6つの型の判定、取材質問を登録し、`kizashi fetch` で公表資料を取得して理由を調べる。
4. `review-lead`（Skill）で点検し、結論の案を登録して `kizashi check <lead_id> --run <run_id>` を通す。
5. `kizashi render <lead_id> --run <run_id>` で候補のメモを、`kizashi render <run_id>` で実行の概要を書く。

記録はすべて `data/runs/<run_id>/` にある：台帳 `ledger.sqlite`、品質レポート `quality_report.md`、登録した提案 `accepted/`、追加資料のページ別テキスト `evidence/`、メモ `memos/`、伏せた写し `public/`。取得した原本は `data/raw/<sha256>.<拡張子>` に保存し、書き換えない。

## メモの読み方

候補のメモは `data/runs/<run_id>/memos/<候補ID>.v<番号>.md`、実行の概要は `memos/run_summary.v<番号>.md`。番号は書き出すたびに増え、前のメモは上書きしない。

冒頭の2行：

- 「調査用・記者未確認。調査の端緒であり、不正の指摘ではない。」——記者が確かめる前のメモであることを示す。`check` の合格や「検査済み」の主張は、記者の確認ではない。
- 「調査用の設定で実行：はい／いいえ」——`scripts/investigate` の設定で実行したか。実行ID、メモの番号、検証記録のハッシュ。

| 節 | 読むところ |
| --- | --- |
| 1 状態と範囲 | 結論と説明の状況、問い、比べた年度、収録範囲、母集団の絞り込み（あれば記者の指示と条件）、使った公表一覧の資料、実行ID |
| 2 検出した変化 | 検出SQL、比べた値（計算ID付き）、年度の系列、比較の条件（母集団、1行の意味、期間、単位、主体の対応、算式）、比較できない理由、同じ区分の変化のほかの件数 |
| 3 照合済みの記載と計算 | 主張ごとの種類（原資料の記載・観測・公表元の説明・仮説）と根拠の位置、計算に加わったレコードと式、資料の一覧（資料ID・URL・取得日時・保存場所・SHA-256） |
| 4 説明の検討 | 6つの型の判定（支持・否定・未確認・対象外）と根拠・探した範囲、説明を反映した値と残る差、仮説と取り下げ条件の結果 |
| 5 言えないこと | このメモから言えないこと（定型文「CSVとPDFの一致は元の記載の正しさを示さない」を含む） |
| 6 次の取材質問 | 相手、問い、必要な資料、何が分かれば判断が変わるか、情報公開請求の候補 |
| 7 記者の確認リスト | 記者が原本で確かめる行。照合できなかった行と項目が先頭。CSV の保存場所、「NO」の値、表計算ソフトでの行番号の目安、PDF のページ、確かめる項目と値 |
| 8 再現情報 | 実行ID、規則の版、コードのコミット、モデルと Claude Code の版、Skill とルールのファイルのハッシュ（開始時と書き出しの時点）、検証記録のハッシュ |

結論の3種類：

- **比較成立**：比較を誤らせる説明（取り込み・公表形式の誤り、集計範囲・期間の違いなど）を否定でき、両年度の行が同種業務の対応で覆われている変化。理由が分かったという意味ではない。理由は「説明の状況」を見る。
- **見かけの変化**：集計範囲・期間の違い、主体の同一性、取り込みの誤り、公表形式間の食い違いのどれかが、根拠付きで支持された変化（単価契約、年度途中、様式の変更、法人番号の桁落ちなど、データの問題による変化）。
- **保留**：比較の条件を公開資料で確定できない、原本照合ができない、または探索の上限に達した。足りない資料と、照会先・情報公開請求の候補が6節に出る。

説明の状況（比較成立のとき）：**全部**（根拠のある説明で変化の全部を説明できる）、**一部**（残る差がある）、**範囲不明**（説明はあるが、どこまで説明できるかを確かめられない）、**なし**（公表資料に説明が見つからない）。

失効：メモを書いた後に台帳の中身（主張・判定・計算・資料の新しい版など）が変わると、`kizashi inspect <候補ID> --run <run_id>` がメモを「失効」と表示する。`check` と `render` をやり直すと新しい番号のメモができる。規則の版（`rules_version` など）が実行の記録と違うと、`check` と `render` は `E_RULE_VERSION` で止まる（新しい実行で調べ直す）。

## メモの読み直し（別のセッション。P1）

`render` の後に、候補のメモを、読み取り専用の別のセッションで Claude に読み直させることができる（設計書9.3）。記者がリポジトリの直下で次のように起動する（開発には使わない）。

```text
scripts/review-memo <run_id> <lead_id>
```

- 最初の指示に、その候補の最新のメモ（`memos/<候補ID>.v<番号>.md` の番号が最大のもの）のパスと、資料のページ別テキストの場所（`evidence/<資料ID>/pages/<ページ番号>.txt`）を入れ、「否定の根拠が支えになっていない箇所、言い過ぎ、根拠の位置が主張を支えていない箇所を挙げる。書き込みはしない」と頼む。指摘ごとに、メモの節、主張ID か型（T1〜T6c）、根拠の資料IDとページを書くよう頼んでいる。
- 起動の設定は `--permission-mode dontAsk --setting-sources project --tools "Read,Grep,Glob" --disallowedTools "mcp__*"`。使える道具を Read・Grep・Glob に絞り、`--tools` が効かない MCP の道具を別に拒否する。調査用の設定（`investigate.settings.json`）は読まない。最初の指示は `--` の後に渡す（`--tools` と `--disallowedTools` は値を複数取るため。D-075）。
- メモが失効していても起動する。起動の前に `kizashi inspect <候補ID> --run <run_id>` で、メモの状態が「有効」であることを確かめる。
- 読めるのはメモとページ別テキストで、台帳（SQLite）は読めない。公表一覧の CSV の行を根拠にした箇所は、このセッションでは確かめられない（確かめられなかったと書くよう頼んでいる）。
- 同じモデルによる読み直しで、独立した検証ではない。指摘は台帳に入らず、メモの根拠にもならない。記者が指摘を読み、直すときは調査のセッション（`scripts/investigate`）で主張や判定を直し、`check` と `render` をやり直す。
- 引数の数か、実行ID・候補IDの書式（実装仕様3.3）が違うと終了コード2、実行のフォルダーかメモがないと終了コード3で、どちらも Claude Code を起動しない。

書けないことと MCP の道具がないことの確かめ方（初めて使うときと、Claude Code の版を変えたとき。結果は、版・日時・入力欄の下のモードの表示とともに `docs/decisions.md` に書く）。Claude は使った道具を取り違えて報告することがある（D-071）ので、Claude の返事ではなく、画面の道具の表示とファイルで確かめる。

1. 別の端末で、リポジトリの直下で `git status --short` を実行し、出力を控える。
2. `scripts/review-memo <run_id> <lead_id>` で起動し、読み直しの返事を待つ。その間に画面に出る道具の表示が Read・Grep・Glob だけであることを見る。
3. `/permissions` の Deny のタブに、`mcp__*`（出どころが起動の引数）と、`--tools` に入れていない道具（Write・Edit・Bash・WebFetch など）が出ることを確かめる。
4. `/mcp` で、接続している MCP のサーバーを見る。接続しているサーバーがあれば、`/context` の内訳に MCP の道具（`mcp__` で始まる名前）が出ないことを確かめる。サーバーが1つもなければ、MCP の道具がないことはこの手順では確かめられないので、記録に「未確認（MCP のサーバーなし）」と書く。
5. 「リポジトリの直下に review-memo-test.txt を作り、test と1行書いて」と頼み、画面に Write・Edit・Bash などの道具の表示が出ないことを確かめる。Claude がモードの切り替えや `!` での実行を案内しても従わない。
6. `/exit` で終えてから、1の端末で、`git status --short` の出力が1と同じで、`ls review-memo-test.txt` がファイルなし（No such file or directory）を返すことを確かめる。

## 再現の手順（4種類の再現の範囲）

設計書9.12の4種類を分ける。どれも、計算が一致しても解釈が妥当かは別に確かめる。

| 再現 | このリポジトリでの手順 | 範囲と制約 |
| --- | --- | --- |
| 保存した入力からの再計算 | 同じ実行で `kizashi check <候補ID> --run <run_id>` を行うと、メモの基礎集計を台帳で計算し直し（V3a）、原本を別経路の読み込み処理で数え直し（V3b）、派生計算をやり直し（V3c）、依存する資料の原本の SHA-256 を照らす（V2）。第三者は、合成データのテスト（`uv run pytest`）で、計算の手順を手で求めた期待値と照らせる | 原データ（`data/`）は公開しない。テストにも実データの抜粋を入れず、合成データだけを使う（D-007）。そのため第三者は「計算の手順は追試できるが、同じ実データの取得は保証できない」。保存した原本から実行を作り直す操作（取得の代わりに `data/raw` を読む）は P0 にない（`run` は公表元から取得する）。原データの誤りは別の問題 |
| 公開元からの再取得 | 同じ実行設定（`data/runs/<run_id>/accepted/` の最初の `run_config`）で `kizashi run` を行い、メモ3節の資料の一覧の SHA-256 と比べる。実行の中で1つの資料を取り直すときは `kizashi fetch <run_id> --recheck <資料ID>` | 内閣府のファイルは毎月差し替わるため、同じ版を再取得できないことがある。差は新しい版として記録し、古い版に依存する候補のメモは失効と表示される。公表一覧の新しい版は、その実行では正規化しないので、新しい実行で調べ直す |
| 台帳からのメモの書き出し | 同じ台帳で `kizashi render <候補ID> --run <run_id>` を行う | 同じ台帳とテンプレートから、同じ本文と引用の対応が出る（検証記録のハッシュも同じ）。メモの番号、書き出しの時点の Skill のハッシュなどの付帯情報は違う。規則の版が違えば `E_RULE_VERSION` |
| Claude による調査の再実行 | 同じ問いで `scripts/investigate` から調べ直す。メモ8節と台帳に、モデル、Claude Code の版、Skill とルールのファイルのハッシュ、登録した提案（`accepted/`）、判断の履歴（`events`）が残る | 探索の経路や文章の一致は保証しない |

## 公開の手順と、公開しないもの

公開する生成例は、記者が `render --public` の伏せた写しから選んで `examples/` に置き、`examples/publish.manifest` に書き、公開用のコミットを手元で作ってから（push しない）、そのコミットで `kizashi check --publish` を通し、通ったそのコミットを公開する（検査は最新のコミットの一覧との一致を求めるので、コミットの前は不合格になる）。手順、`disclosure.allow`（伏せない名前。記者が書く）、補助資料の一覧（`KIZASHI_DENYLIST`。4点を1行ずつ）の書き方は `examples/README.md` にある。**公開するのは、`check --publish` を通したコミットそのもの（検査の後に変えていないもの）だけにする**（実装仕様12.2）。氏名・受注者名などを検査するのは UTF-8 として読めて 5MB 以下の中身だけで、それ以外（Shift_JIS の CSV、PDF など）はハッシュだけを照らす。合格のメッセージにその数が出るので、0件でなければ記者が中身を確かめる。検査は `examples/` だけでなく、ステージと、すべての参照からたどれる履歴の中身を見る。履歴で見つかったものは作業フォルダーを直しても消えないので、新しいリポジトリを作り直す。

ひな形の状態（`examples/` に `README.md` と `publish.manifest` だけがある状態）で検査が何を見るか：

- 一覧（`examples/README.md` と一覧のファイル自身）と、ステージ・最新のコミットの `examples/` の一覧が一致するか。
- `KIZASHI_DENYLIST` の4点の中身の SHA-256 が、作業フォルダーの一覧のファイル・ステージ・履歴のどの中身とも一致しないか。4点のファイル名が、ステージと履歴のパスにないか。
- `--run` で指定した実行の原本と台帳から作った氏名・取り込まない列の値・受注者名・法人番号が、ステージと履歴のテキストにないか。この中には `docs/`、`references/` の知識ファイル、テストも入る。
- 2026-11-06 時点では、知識ファイル `references/investigative_open_data_catalog_v13.0.md` の19行が、P0-7 の実行の受注者名と同じ文字列で `P_COUNTERPARTY` になる（D-054）。記者が名前と掲載の文脈を確かめ、公開を認めたものを `examples/disclosure.allow` に書くまで、合格しない。

公開するものと、公開しないもの（設計書9.12）：

| 公開するもの | 公開しないもの |
| --- | --- |
| コード、`CLAUDE.md`、Skill、設定の例、分野アダプタ（`datasets/`）、テスト（合成データ）、評価の方法と結果（`eval/`）、記者が選んだ生成例と実行記録（`examples/`）、知識ファイル3点（v13.0。SHA-256 は下）、README | 原データそのもの（利用条件の確認が済むまでは取得手順とハッシュだけ）、`data/` と `inbox/`、補助資料4点、APIキー、個人の氏名、内部用の列（担当官の所在地・相手方の住所など）、会話の全履歴、未確認の実名の仮説、個人の絶対パス |

公開する例とデモ動画では、受注者名と法人番号を既定で伏せる。記者未確認のメモで実在の企業を名指しすることの影響を避けるためである。引用には、候補と関係のない受注者名や法人番号が入ることがある（一覧表のページの引用は、文末までの決まりで長くなる。D-086）。伏せ字と `check --publish` が当てるのは、その実行の公表一覧にある受注者名・法人番号と同じ文字列だけなので、表記の違う名前や公表一覧にない名前は伏せられない。公開する写しとデモ動画では、引用の中の名前も記者が確かめる。

## 限界（設計書11.3の残るリスクの要点）

- 理由をたどる資料（公告・仕様書など）が公開されているとは限らない。理由を調べる資料の経路は未決（D-004）。見つからなければ、見かけの変化と保留を中心にし、誤った比較を止めることを価値として示す。
- 点検（`review-lead`）は調査と同じ文脈で行うので、独立した読み直しではない。独立した確認は、別経路の再集計（V3b）と記者が担う。別のセッションでの読み直し（`scripts/review-memo`。P1）も同じモデルによるもので、独立した検証ではない。
- 強い語（「不正」「疑惑」など）は警告だけで、書き出しを止めない。表現の行き過ぎは記者が確かめる。
- 比較の条件を確定できない候補で、1つの年度の値だけを参照して文で比べる主張は、機械の検査（V5）では見分けない。`review-lead` が点検し、メモの7節で記者が確かめる（D-056④）。
- 権限の設定は、許可した `kizashi` の中の処理には及ばない。`kizashi` は入力の場所・拡張子・パスを検査するが、OS の水準の制限（サンドボックス）は入れていない。P1 で試すと、共通設定の `Edit(/data/**)` の拒否がサンドボックスにも効き、`kizashi run` が台帳を書けなかった（D-079）。取得した資料の中の指示（プロンプトインジェクション）を完全には防げない。テストの SF-1 は、資料の中の指示で `kizashi` の台帳や設定が変わらないこと（取得の処理）を確かめたもので、資料を読んだ後の Claude の振る舞いは試していない。
- 内閣府のファイルは同じ URL のまま差し替わることがある。`fetch --recheck` で取り直してハッシュを比べる。
- 知識ファイルに誤りや版の更新がありうる。メモの根拠にはしない（V2）。
- 追加資料のページ別テキストでは、実行の担当官の氏名（公表一覧の担当官の列にある氏名）を「（氏名）」に替えて保存する。それ以外の氏名は見つけられない。`check` は、引用したページ別テキストを原本から抽出し直して比べ、文書値を引用の数値と照らし直す。台帳や `data/` を直接書き換えた場合の検出は、この2つと原本の SHA-256（V2）、計算のやり直し（V3）の範囲に限る。
- 調査のセッションの Claude が、使った道具を取り違えて報告することがある（Read で読んだのに「tail を実行した」と返した。D-071）。操作を確かめるときは、画面に出る道具の表示（Read・Bash など）で確かめる。
- 「記者未確認」のメモが確かめられないまま使われるおそれがある。冒頭の定型文と記者の確認リストで示し、公開は記者が一覧を作り検査を通した場合だけにする。
- 上限：詳しく調べる候補3件、追加資料12件、通信40回、修正2巡（設計書4.3）。上限に達したら保留にする。
- 評価（`eval/`）は件数が少なく、まだ行っていない（ひな形）。精度の数字を宣伝しない。
